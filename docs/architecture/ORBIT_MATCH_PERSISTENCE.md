# Orbit Match persistence

Match uses the existing verified Firebase Player identity and API infrastructure. It does not change the authoritative venue state, player profile transport, membership, waitlist, or tournament-interest contracts.

Tournament discovery follows the existing API cursor with a client bound of twenty fifty-venue pages. Club-scoped event records and owner-scoped interests merge in encounter order; later withdrawals remove earlier active interests. A later request failure, invalid continuation or page cap leaves the result explicitly partial. An authenticated account change rejects the entire scan. This does not add a discovery authority or permit private-to-public fallback for tournament data.

Match tracks cash/venue and tournament freshness separately. Unconfirmed events cannot remain actionable recommendations or Saved targets. A missing saved event is treated as not loaded until both the venue catalog and tournament catalog are ready and complete. Fresh cash recommendations remain available during an independent tournament failure. Selected-format discovery status also controls loading/empty telemetry, and incomplete feeds do not emit a complete empty result. See the [scoped verification record](../agent/tasks/2026-10-14-player-tournament-catalog.md).

## Private state and mutations

The API owns `players/{firebaseUid}/orbitMatch/state`. The Player-facing snapshot contains schema version 1, a monotonically increasing revision, a separate preferences revision, structured preferences, candidate decisions, the last undo target, recent minimal events, and the last 500 acknowledged mutation IDs. Only the verified owner may read this exact document through Firestore; every client write is denied. Deleting accounts also lose read access. API access uses the existing App Check, verified Firebase Auth, and active-account middleware.

`GET /player/match` returns `{ "ok": true, "state": ... }`. It creates a missing state in a transaction, seeding only existing favorite venue IDs, recognized generic NLH/PLO preference IDs, and an unambiguous numeric small-blind/big-blind pair. Arbitrary game IDs and free-text stakes are not inferred. A legacy search radius did not enable a geographic filter, so it does not silently become an active Match constraint. Subsequent profile edits never overwrite Match preferences.

`POST /player/match/operations` accepts a single `MatchOperation` directly and returns the same envelope. Operations decide/save/pass, conditionally remove a decision, conditionally undo the latest swipe, compare-and-swap preferences, or record a minimal event. Saves do not join a waitlist or express tournament interest. Preference and decision conflicts return HTTP 409 with a specific `MATCH_*_CONFLICT` code. A stale removal or undo cannot overwrite another device's newer decision.

The transaction reads the deletion marker together with Match state. This closes the race between an initial authorization check and an account deletion. Every accepted operation atomically writes a backend-only receipt at `players/{firebaseUid}/orbitMatch/state/receipts/{mutationId}` containing a canonical payload digest and server receipt time. Retrying the same ID/payload returns current state without applying it twice; reusing that ID with different data returns 409. Receipts remain until account deletion so old offline requests cannot reapply after a recent-ID ring expires. They contain no copied account, operation payload, coordinates, or availability snapshot.

## Bounds, privacy, and cleanup

Operation bodies are limited to 16 KiB. IDs and preference lists are validated; labels are bounded to 200 characters, venue lists to 100 IDs, radius to 1–500 miles, and waitlist preference to 0–10,000. The state has a 900 KiB safety ceiling below Firestore's document limit. Saves are never silently evicted to make room; a storage-capacity failure is explicit and leaves the existing document intact.

Events retain at most 200 entries and recent passes at most 300, each for at most 30 days from server receipt. Saved references persist until removed or the account is deleted. Expired history is pruned on a later state read/write, not by a background deployment. The recent acknowledged-ID ring supports client projection; permanent private receipts provide authoritative idempotency. A `waitlist-success` event must reference the current saved decision and candidate. It is a client-reported attribution after the existing waitlist response, not server proof of attendance, payment, or a reserved seat. Analytics failures must not block the waitlist workflow.

Match state and location stay separate from `PlayerAccount`. Current membership and waitlist builders include the supplied player object, so keeping these domains separate prevents accidental history/location disclosure to venues. State stores public candidate references and bounded display summaries only; it does not persist club-controlled availability, floor details, occupants, contacts, or precise device location.

The existing recursive account cleanup removes the entire Player subtree. Its compatibility fallback now removes Match receipts in bounded 200-document pages, Match state, private identity, and the root profile. Unrelated owners remain untouched. A secure pending-operation journal must join existing local account cleanup and preserve same-UID/version acknowledgement semantics.

The native adapter rejects writes to the Match journal and local-origin keys when Expo SecureStore reports unavailable. It never acknowledges those writes through the existing volatile profile fallback or plaintext storage. Actual native write failures also propagate before optimistic projection; retry can persist after secure storage becomes available. Existing profile/auth fallback, alert storage, legacy migration, reads and account cleanup are unchanged. This is a mocked native-adapter/controller test boundary; supported-device secure persistence remains a separate runtime gate.

Exact-document subscription needs no composite index. Field exemptions disable indexing on Match preferences, decisions, undo, events, and recent mutation IDs. After the user explicitly authorized the Firebase target named tabletalk-server (CLI-resolved project `tabletalk-s`) and the existing production API, root released the reviewed Match rules and these five exemptions successfully. The generated release input preserved all fifteen live composite indexes and two existing field overrides; four unrelated baseline TTL proposals and private-games cleanup were excluded. `out/orbit-match-firebase-deploy.log` records compilation/index deployment/rules release and exit0. The tested API artifact was also promoted successfully to `orbitapp-one.vercel.app`; ordinary exact-origin probes passed health/version/privacy200 and signed-out Match401, with released artifact SHA `610b16cddebfe95cfd2721fff3edc8e7e7fa9f1a`. The [authorized release record](../agent/tasks/2026-10-12-orbit-match-authorized-release.md) owns full provenance/results. No authenticated hosted Match mutation is claimed.

## Interaction history and conversion attribution

The operation reducer records accepted save, pass, and undo actions. The Player controller also submits minimal opened, impression, details, saved-revisit, empty, load-failed, and waitlist-success events. Event bodies contain a kind, an optional public candidate reference, and an optional saved-decision mutation ID. The API derives the owner from authenticated identity and stamps receipt time; events contain no email, phone, document fields, origin, table occupants, or copied availability. Save/pass decisions affect only that candidate. A pass is not a venue exclusion, and a save is not attendance or a waitlist request. Optional unfamiliar-venue ranking can use current favorites/saved references with a capped influence; it does not infer attendance or venue dislike.

History is first-party, client-reported telemetry rather than trusted proof of a venue outcome. The API validates shape, ownership, and current saved-decision attribution, but does not independently verify that a card was displayed or a waitlist request succeeded. It must not be used for billing, guaranteed seats, admission, or priority. There is no third-party analytics SDK, identity export, or separate analytics warehouse in this implementation.

For the conservative waitlist conversion path, an immediately eligible request initiated from Match details attaches an optional local context to its own `SeatRequestDraft`: the current UID, current saved-decision mutation ID, and start time. The draft already owns the selected venue/game. An already active request is not a new conversion, and a redirect awaiting membership activation does not retain Match context. Canceling that draft or opening a new draft drops the context. It is never added to the API waitlist payload or a global same-game attribution record.

Only the existing successful response callback for that confirmed request may submit waitlist-success, passing the actual request ID and that draft's context. The UID must still match and the response must arrive within ten minutes. The current save must still exist with the same mutation ID when the API accepts the event; a newer removal or replacement causes attribution rejection. The existing request still requires its own confirmation, current venue/membership/age validation, idempotent API action, and authoritative result. Saves, unsaved recommendation requests, canceled or unrelated requests, failures, other games/accounts, and late responses are not conversions. A recorded conversion indicates a client-confirmed request response, not a seated player, reserved seat, payment, or tournament registration. The Match event does not persist the request body or request ID; it remains untrusted client attribution rather than an independently verified backend join.

Event writes are best effort, use ordinary operation IDs, and cannot change a successful venue request. The controller currently deduplicates `(kind, candidate reference, save mutation ID)` within its lifetime, retaining at most 500 seen keys. This means retained event counts are sampled unique interactions in a controller session, not a complete count of every repeated tap or app open. The 200-event/30-day history and failed/offline telemetry also limit any later rate calculation. No production aggregate rate or complete conversion funnel is claimed. Any later reporting must state its denominator, window, deduplication, and untrusted-client limitations.

The pure [retained-history summary](../../player-app/src/domain/orbitMatchAnalytics.ts) supports local pilot reports without adding collection, a server analytics API, or an external SDK. Save/pass shares use retained accepted decision-event samples; undo stays a separate sample and does not erase those actions. Detail-open rate uses unique candidate references with retained impressions as its denominator and credits only a later detail sample in that cohort. Saved-revisit rate uses unique retained save-event references and later revisits. Current-saved-mutation waitlist rate uses only current saves whose exact mutation/reference also has a retained save event, and credits unique later `waitlist-success` samples with that exact attribution. Removed/undone saves, missing predecessor samples, malformed references, and unrelated conversions remain orphan counts. A zero denominator returns `null`, and repeated samples cannot produce a rate above one. Output contains only aggregate numbers, observation/window timestamps, and fixed sampling explanations; no account identity, candidate/event/mutation IDs, coordinates, or venue labels are emitted. It enforces the existing 30-day/200-event bounds and reports excluded age/future/invalid/duplicate/capped samples, with an at-cap warning that earlier history may be missing. Logged opened/empty/load-failure counts are samples, not complete session totals. The local QA result consumes the helper from its final server-state scenario and labels that scope explicitly because the harness resets between checks; it is not a combined funnel for the full test run or evidence of attendance.

## Future Orbit Match+ extension points

The initial experience remains available to ordinary users. There is no Match paywall, billing implementation, premium-only inventory, paid swipe allowance, venue priority, or guarantee of seating. The 100-pending-operation journal and document byte ceiling are identical durability/resource backpressure for all accounts; they are not purchasable entitlements and do not evict previously saved games.

The pure [candidate/ranking module](../../player-app/src/domain/orbitMatchCandidates.ts), typed [Match domain](../../player-app/src/domain/orbitMatchTypes.ts), controller persistence port, and backend transaction service provide separate extension points. A future explicitly authorized entitlement context can select extra ranking configuration or additional preference UI without replacing identities, live venue sources, operation replay, or existing requests. Entitlements must be verified by the backend for any protected operation; hiding a control is not authorization. Extra saved preference profiles would need a reviewed owner-scoped, versioned schema and operation extension, preserving current state and old-client decoding. Advanced alerts would need a separately authorized backend delivery workflow using existing infrastructure, rather than a new client publisher or per-card listener. These are architectural boundaries, not implemented paid features.

Future personalization must retain explicit exclusions/strict constraints, conservative missing-data behavior, bounded feedback influence, and factual explanations. Future entitlements must never alter venue-controlled eligibility, seat counts, membership/age gates, waitlist ordering, or tournament participation. No additional subscription or payment dependency is introduced by these extension notes.

## Validation boundary

Fake-store tests cover concurrent devices, long-offline idempotency, payload-ID conflicts, preference compare-and-swap, conditional undo/removal, owner isolation, deletion fencing, malformed state, retention, and fallback cleanup. Rules emulator coverage checks owner/other/anonymous/unverified access, client-write denial, receipt privacy, and deletion blocks. Static rule checks do not substitute for emulator execution or controlled pilot verification.

`npm run test:firestore-rules` also includes [real Match persistence integration](../../tests/orbitMatch.firestore.emulator.test.js). This optional suite runs only with Firestore at `127.0.0.1:8085` and project `demo-orbit-release-ci`; foreign targets fail before SDK initialization. It uses the existing Admin-backed database adapter, a demo-only Admin app with an ephemeral RSA fixture certificate generated in memory, and a local Express server mounting the real GET/POST handlers. No real credential, credential file, ADC cache, or Auth service is used; the SDK endpoint is explicitly pinned to the local emulator. HTTP identity is a clearly labeled verified-UID test stub: this suite does not validate Firebase Auth or device sign-in. Tests cover a new adapter/session restoring data, concurrent HTTP idempotency, actual SDK transaction retries after injected ABORTED errors, cross-device conflicts, and a deletion marker introduced between transaction attempts. A real owner snapshot listener observes API revisions under the committed rules; another owner's listener is denied. These rules contexts also use local test claims. The rules and integration files run serially because the rules suite clears the demo database between tests. Ordinary unit runs skip the real persistence cases when the emulator host is absent; target-isolation tests still run.

The platform-neutral reducer is [orbitMatchState.cjs](../../apps/api/src/shared/orbitMatchState.cjs); public Player types are [orbitMatchTypes.ts](../../player-app/src/domain/orbitMatchTypes.ts). API persistence belongs to [orbitMatchService.js](../../apps/api/src/orbitMatchService.js), and route registration to [orbitMatch.js](../../apps/api/src/routes/orbitMatch.js).

The same guarded suite now adds a real venue state/publication/licensed-discovery case. It commits authoritative revisions, runs the canonical REST publisher against the emulator through an owned-path loopback wrapper, and uses the real public API license inspector/Player decoder/candidate and saved reconciliation. It verifies availability update, table end, revoked-license exclusion and private DTO filtering. Match saves remain private and intact. Public discovery reads authoritative account state, while canonical projection is a separate consumer of that revision; the test does not run the outbox scheduler, OAuth provider, real Auth/device, or a native screen.
