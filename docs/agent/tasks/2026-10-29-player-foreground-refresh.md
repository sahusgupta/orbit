# Preserve Player foreground refresh invalidations

This focused change starts from main `9c726a55fc353c0edda31c6d1e8843c76a8a652c` on `codex/reliability-player-foreground-refresh`. It changes the internal polling owner, the two repository subscriptions, same-boundary tests and this record. Public method signatures, authentication, API/data schemas, publication/revision semantics, retry behavior, dependencies and both 60-second polling intervals remain unchanged.

## Observed failure and narrow ownership boundary

The real [application lifecycle binder](../../../player-app/src/application/playerSubscriptionLifecycle.ts) refreshes on foreground return. The [club subscription](../../../player-app/src/data/subscriptions/clubSnapshotSubscription.ts) and [tournament subscription](../../../player-app/src/data/firebase/playerTournamentRepository.ts) previously returned their current promise without remembering that a newer explicit refresh was needed. A foreground return during an older request could therefore publish that older result and wait until the next 60-second poll for current data. Notifications queued from a response callback could also be lost before the old promise's external cleanup ran.

The small [polling owner](../../../player-app/src/data/subscriptions/playerPollingSubscription.ts) now remembers one pending explicit refresh while a catalog operation is running. It publishes one owned completion before invoking the read, preserving immediate fetch start and identical returned promises for overlapping callers. It drains a needed follow-up without overlapping reads. Ownership release and the final pending-work check occur in the same continuation, so a notification either marks the current drain dirty or starts a new owner. Intermediate results still reach the existing callbacks during continuous invalidations.

Timer ticks use a private non-invalidating path: a tick during an active read shares it without requesting a trailing read. `startPolling` clears only the previous timer, preserving work just queued by a foreground refresh. `stopPolling` and unsubscribe clear pending work and the timer. Retired handles cannot recreate an idle timer. Existing in-flight reads are allowed to finish; the repository's original local disposal guards suppress retired callbacks. The existing eager initial read while backgrounded remains intact.

Each repository retains its original fetch → success/catch/error callback chain, including stale club fallback, partial metadata and UID/session checks. A handled failure can be followed by pending work. A throwing error callback still rejects the shared task, clears ownership/pending work and permits a later explicit refresh to recover. The public object still exposes exactly `refresh`, `startPolling`, `stopPolling` and `unsubscribe`.

The completion waits for dirty-drain quiescence and can remain pending during endless explicit invalidations. Actual production refresh callers are the lifecycle binder's `void subscription.refresh()` calls; UI actions do not await this completion for busy state. Ordinary timer ticks cannot keep the dirty drain alive. No mutation reconciliation or transport authority is moved into the scheduling helper.

## Characterization and deterministic resource evidence

Before extracting the owner, 12 new [actual repository/lifecycle characterizations](../../../player-app/src/data/subscriptions/playerPollingLifecycle.test.ts) and the two existing lifecycle cases passed against unchanged production source. They preserve immediate reads, shared-promise identity, handled failures, the club success-callback-to-stale-error path, tournament onError routing, throwing error callback rejection/recovery, interval coalescing, retired callbacks/timers/refreshes, and the initial background read.

The expanded actual-boundary file then had 14 expected failures / 20 passes before the runtime change. Both real repositories and the real lifecycle binder execute; only HTTP, Firebase client/auth and the forbidden local fallback are mocked. No synthetic replacement subscription is used. After the change all 34 cases pass. Two [helper completion tests](../../../player-app/src/data/subscriptions/playerPollingSubscription.test.ts) complement that coverage: one schedules a new owner after the final read but before the previous completion settles, and one preserves a synchronous operation error plus later recovery.

Deterministic one-page fixtures show:

- A burst of 1,000 explicit invalidations during a read requires exactly one follow-up: two total catalog reads, one unique returned completion, and maximum active page request count one per subscription. The original code already shared a completion, but incorrectly dropped the needed follow-up; this change preserves bounded promise cardinality while restoring freshness.
- A newer invalidation during that follow-up produces one further read, with callbacks delivered for all completed revisions. Four continuously invalidated reads deliver four intermediate callbacks without starving progress.
- Three overlapping timer ticks during a long read produce no trailing request. Background/stop and disposal drop queued work. Replacing account A with B starts B independently, suppresses A's late callbacks, and does not replay A's queued read.
- A retired handle's `startPolling` previously recreated one idle timer; it now creates none. This is timer ownership evidence, not a battery or CPU-throughput measurement.

The necessary follow-up can increase reads compared with the buggy dropped-invalidation behavior. No blanket server-read, quota, billing, heap-byte or production-latency reduction is claimed. Maps/data/session state are not globally shared; each subscription has its own bounded owner and one pending bit. These are synthetic request/timer/promise counts, not device or production load measurements.
