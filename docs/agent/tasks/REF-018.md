## New orchestration characterization

Added `src/lib/managementPersistenceBrowser.test.tsx` against unchanged `App` ownership. It pins:

- initial browser load through `last-account`, ahead of the base storage key;
- synchronous per-account browser writes and `last-account` updates;
- browser save publication to the isolated localhost bridge and no desktop call;
- first 404 bootstrap publication, empty payload behavior, optional/offline retry every 1.5 seconds, and no post-cleanup polling;
- latest-state profile/interest merge order, same-state no-op identity, per-account persistence, and membership-notification priority over a simultaneous seat request;
- Firebase reconciliation subscription cleanup even when renderer Firebase authentication is disabled.

Added `src/lib/managementPersistenceDesktop.test.tsx` with fully mocked preload and Firebase adapters. It pins:

- full-state desktop startup load followed by newer-cloud replacement;
- stale cloud timestamps retaining desktop state and cloud failure retaining desktop state;
- browser + desktop + Firebase save fan-out, with no localhost bridge publication when the preload exists;
- update preservation using the latest rendered state and cleanup of the replaced update listener;
- 3-second desktop profile/interest polling, authoritative merge order, seat-request notification, optional API failure, and retry;
- listener/30-second Firebase reconciliation of profiles, interests, tournaments, and revenue; failed reconciliation retry; desktop save failure surfacing as `error`; later success returning to `saved`;
- authenticated startup/poll ordering: a poll can merge into the latest local `stateRef` before startup propagation, so non-profile/interest fields remain from that latest local state while the polled collections merge;
- interval, subscription, and update-listener cleanup on unmount.

The new tests use only jsdom, fake timers, local storage, synthetic records, a deliberately mocked localhost bridge, mocked preload methods, and mocked Firebase adapters. They open no socket and use no production service, credential, database, provider, or unsafe stress harness.

## Preserved policy map for REF-019

1. Browser initialization reads the `last-account` target first; it consults the base key only when that lookup has no value. Missing or malformed selected data returns normalized seed state.
2. Desktop startup normalizes and stores the preload record. With renderer Firebase enabled, missing cloud state publishes the desktop state; stale cloud state is ignored; newer cloud state replaces the full state; cloud errors are optional.
3. Account-key restore asks the preload first and uses the per-account browser record only when the preload is missing, empty, or fails. The supplied pilot access replaces the stored access before normalization/persistence.
4. Every normal save writes browser account state and `last-account` synchronously. It then uses the preload save when present, otherwise posts to the optional localhost bridge; enabled Firebase publication is fire-and-forget. User-visible save success/failure follows the preload/browser promise, not cloud completion.
5. The localhost bridge merges profiles/interests into the latest local state and persists them locally without an undo entry. Desktop polling merges those two collections without a local re-save. Firebase reconciliation merges profiles/interests/tournaments/revenue, adds one undo snapshot, and saves the merged state.
6. Membership requests win notification selection over simultaneous seat requests. Notification records are deduplicated by ID, newest-first, capped at 100, and browser-persisted.
7. Optional bridge/API/Firebase read failures are swallowed and retried by their existing interval/listener. A failed save after a successful Firebase reconciliation keeps the merged state but exposes the exact error status.
8. All intervals and listeners stop on cleanup; an in-flight Firebase sync can queue one follow-up pass.
