## Scope

Two recovery defects surfaced in current call sites:

- Two offline preference edits can have bases 0 and 1. If another device commits different preferences at revision 1, the first local edit conflicts, but dropping only that edit lets its dependent successor match the unrelated revision and overwrite it. The existing journal stores numeric base revisions, not preference ancestry. Projection also skips the rejected ancestor and applies the successor, and unrelated successes can erase the conflict message.
- Clubs derives a ready selection while loading if memberships are retained. A manual retry retains old clubs while setting loading, so the wallet/QR and game panels can remain mounted before a successful refresh. Existing action/server validation still applies; this is a stale-affordance defect, not evidence of an authorization bypass.

The intended changes preserve the API, persisted journal/state shapes, mutation identities, account isolation, server CAS rules and card/disclosure design. Valid sequential offline preference edits remain supported. An unresolved preference chain must not project or send orphan successors; a definitive rejection retires only its unacknowledged preference tail while preserving independent operations. Reconciliation must be durable before memory changes, and conflict feedback must survive unrelated successes. A fresh explicit preference edit can proceed after reconciliation. Retained Clubs rows remain readable while action-bearing panels wait for refreshed data.

No production probe, provider operation, deployment or new iPhone build is part of the initial reproduction. The prepared `71c251af` package-inspection helpers remain unexecuted; any replacement candidate must bind actual reviewed source and a real submitted job before inspection.
