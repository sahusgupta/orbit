# REF-019: Extract management persistence and synchronization application layer

Status: `complete`

Date: 2026-08-08

## Objective

Move management browser, Electron preload, optional localhost bridge, and renderer Firebase selection; publication; reconciliation; save-result policy; account restore; update preservation; pilot refresh; and staff-request notification policy out of `App` without changing persisted shapes, precedence, retry cadence, merge order, failure text, or protocol-v2 behavior.

## Characterization gate

Immediately before the first production move, the REF-018 boundary passed 4 files / 18 tests:

- `src/lib/accountRestore.test.ts`
- `src/lib/firebaseClubSync.test.ts`
- `src/lib/managementPersistenceBrowser.test.tsx`
- `src/lib/managementPersistenceDesktop.test.tsx`

That unchanged-production boundary pins last-account selection, desktop/cloud timestamp precedence, browser/preload/bridge/Firebase save fan-out, optional-service failures and retries, profile/interest/tournament/revenue merges, notification priority, update preservation, save status, queued reconciliation, and cleanup. It was rerun after every cohesive production move.

## Implemented ownership

### Browser and platform adapters

- `src/app/persistence/browserStateRepository.ts` owns initial browser selection, per-account keys, the last-account marker, safe parse/normalization fallback, local account restore, local writes, and storage-event selection.
- `src/app/persistence/managementPersistence.ts` owns the injectable browser/preload save result policy, optional localhost publication/read status mapping, desktop startup/account operations, update preservation registration, pilot validator access, and desktop-first/local-fallback account restore.
- Normal saves still write the browser partition synchronously, then select preload or localhost publication. Enabled Firebase publication remains fire-and-forget, and visible success/failure still follows the local/preload promise.

### Application synchronization

- `useManagementStartupSync.ts` owns desktop startup normalization, browser mirroring, cloud timestamp precedence, missing-cloud publication, and the authenticated first-snapshot retry flag.
- `useManagementPlayerUpdateSync.ts` owns the 1.5-second localhost loop, 3-second desktop API loop, and listener/30-second Firebase reconciliation. Existing merge widths, no-op comparisons, undo behavior, messages, retry policy, one-pass queue, and cleanup are unchanged.
- `useManagementPersistenceEvents.ts` owns cross-window state reload and Electron update preservation.
- `useManagementPilotAccessRefresh.ts` owns the 5-minute server-managed license refresh and one-time migration publication.
- `staffRequestNotifications.ts` owns membership-first/seat-second selection, newest request choice, ID deduplication, 100-record cap, read updates, and browser storage.

`App` now initializes through the repository, invokes the persistence service for normal/undo saves and existing-account restore, and composes the hooks. Its remaining direct preload calls concern backend display status, telemetry/errors, report submission, and auxiliary window navigation—not management state persistence or synchronization algorithms.

## Preserved contracts

- No `AppState`, `PersistedAppState`, preload IPC, API, Firebase collection/document, protocol-v2, authentication, authorization, or database shape changed.
- Browser last-account/base precedence and malformed/missing fallback remain unchanged.
- Desktop state is applied before optional Firebase comparison; stale cloud records remain ignored and newer records replace the full state.
- The characterized authenticated startup/poll ordering remains unchanged: an early desktop poll may merge profiles/interests into the latest local `stateRef` before startup propagation.
- Local bridge and desktop polling merge profiles/interests only; Firebase reconciliation additionally merges tournaments/revenue and records one undo snapshot.
- Optional read/publication failures remain swallowed and retried by their existing trigger. Visible save and player-sync failure messages remain unchanged.
- No production runtime, network service, credential, provider, database, Electron process, or unsafe stress harness was used.
