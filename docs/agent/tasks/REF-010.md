# REF-010 - Split API database and route responsibilities

Status: active

## Objective

Separate the API's SQLite connection/schema, focused persistence repositories, HTTP middleware, route groups, app composition, and process startup while preserving every public route, authorization boundary, database schema, persisted shape, service integration, logging path, startup/export behavior, and failure response.

## Evidence

- `apps/api/src/database.js` is 556 lines and combines path selection, SQLite lifecycle/schema, client mapping, telemetry/update/error history, account state, venue summaries, and analytical reports.
- `apps/api/src/server.js` is 668 lines and combines process bootstrap, authentication, domain logging, static assets, dashboard/SSE, Player/payment routes, client telemetry, account state, reports, the error boundary, and signal shutdown.
- `apps/api/src/database.pagination.test.js` protects telemetry cursor ordering but does not characterize the other facade responsibilities.
- The API package is CommonJS and starts through `node src/server.js`; the module also exports the Express app for its hosting boundary. Both behaviors must remain intact.

## Safety boundary

- Never open or modify tracked `data/orbit-api.sqlite3` or `apps/api/data/`.
- Database tests must use unique files under the OS temporary directory and close/remove the database, WAL, and SHM files.
- HTTP characterization may start only a child API bound to `127.0.0.1`, with a unique temporary SQLite file, synthetic auth values, and Firebase/Stripe/RevenueCat credentials explicitly disabled.
- Do not invoke state publication, valid privileged identity/payment calls, licenses, hosted endpoints, production data, deployment, package, or release commands.
- Preserve the `./database` facade and `server.js` entrypoint/export so existing scripts and deployment metadata do not need a contract change.

## Sequence

### REF-010A - Characterization

Commit tests against unchanged production code for:

- database path selection and reserved Postgres rejection;
- client insert/update mapping, filters, retained update status/event, and close/reopen persistence;
- update, telemetry, error, summary, cursor, and details behavior;
- validated state save/load/latest, malformed-state rejection, venue aggregation, and report storage;
- public health/legal routes and request IDs;
- dashboard authentication/static delivery;
- Player/webhook ordering before client authentication without valid external credentials;
- client authentication, heartbeat persistence, owner reads, state misses, reports, and centralized JSON errors.

### REF-010B - Database repositories

Move connection/schema, clients, telemetry, state, and reports into focused `apps/api/src/db/` modules. Keep `apps/api/src/database.js` as the stable facade and keep one process-local connection owner. Do not change SQL, transaction order, limits, mapping/default behavior, IDs, timestamps, or exported names.

### REF-010C - HTTP composition

Move middleware and cohesive route groups into focused modules, introduce a non-listening app composition boundary, and leave process listen/signal shutdown in `server.js`. Preserve middleware/route order, body parser placement (especially raw Stripe payloads), exact status/body/header behavior, static paths, SSE ownership, service calls, and `module.exports = app`.
