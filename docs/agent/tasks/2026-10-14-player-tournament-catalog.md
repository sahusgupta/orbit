## Observed problem and scope

Tournament discovery fetched one fifty-venue page, while cash discovery already followed bounded pagination. The live-data hook discarded tournament page completeness and retained tournament rows after an independent refresh error. Match treated the cash feed's readiness as readiness and completeness for both kinds. This could leave stale events in recommendations or call a saved event outside the loaded prefix unpublished.

The client now aggregates at most twenty fifty-venue discovery pages. Tournament identity remains `(clubId, tournamentId)`; interest identity remains `(clubId, tournamentId, playerId)`. Last encountered payloads replace earlier payloads without changing first insertion order. Withdrawals merge before active interests are selected. This ordering does not claim timestamp freshness. An initial request failure throws; a later failure retains a partial prefix. Invalid or cyclic continuation cannot claim completeness. Signed-in ownership is checked around every awaited page and before returns; a changed owner rejects the entire private result. Public discovery remains public and does not gain private interests if authentication changes midscan.

Separate ephemeral tournament readiness and partial flags flow through the existing session. Fresh cash remains usable while events load or fail. Unconfirmed events leave the Match catalog, saved decisions remain, and missing saved events are called unpublished only after both required catalogs are ready and complete. Home event counts and Events loading, partial and error copy use the corresponding feed state. No server contract, stored Match shape, Firebase paths, rules, indexes, authentication policy or mutation validation changes are in scope.
