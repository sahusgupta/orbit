# REF-026: Validate renderer Firebase input boundaries

Status: `complete`

Date: 2026-08-10

## Objective

Replace the renderer Firebase cloud-state, membership-request, and waitlist-request assertions with explicit validation and known legacy normalization before external records enter canonical management transforms. Preserve paths, protocol-v2 publication, per-club scoping, request source order, duplicate/idempotency behavior, applied acknowledgements, canonical state shapes, and retry/fallback semantics.

## Characterization gate

Commit `fcefbc1` added malformed-input fixtures against unchanged production source. The gate records:

- valid cloud envelopes are returned with their existing data;
- an existing Firestore document whose data is null produces the existing null fallback;
- current-path records precede legacy-path records;
- duplicate IDs across those paths apply only once;
- malformed records already marked `applied` short-circuit before field access;
- legacy membership/waitlist requests without a type discriminator remain accepted;
- a null pending request rejects the reconciliation pass before state mutation or acknowledgement.

The unchanged-production gate passed 3 files / 37 tests and all four root compiler projects. Firebase App/Auth/Firestore were fully mocked; no SDK connection, credential, production record, or remote service was accessed.

## Implemented boundary

`src/lib/firebaseClubDecoders.ts` now owns:

- cloud record/object/settings and known collection-container validation;
- canonical membership and waitlist request construction from `unknown`;
- optional discriminator compatibility for legacy requests;
- normalization of legacy unknown waitlist action/attendance values to the existing join/interested fallback;
- optional player preference normalization to an empty list;
- minimal ID/status marker reads that preserve duplicate/applied short-circuit order;
- Firebase error-code inspection without an assertion.

`loadClubStateFromFirebase` returns a typed persisted-state result from the decoder instead of trusting a generic caller assertion. `decodePersistedAppState` is the shared object/settings envelope validator used by both JSON persistence parsing and Firebase decoding. `syncPlayerUpdatesToClubState` reads only the ID/status marker first, then decodes a canonical request only when it is neither duplicate nor applied.

Tournament registration and revenue transaction records already used explicit parsers and were not redesigned. The internal recursive `stripUndefinedForFirestore<T>` assertions remain generic output-preservation mechanics, not external input assertions.

## Preserved behavior and security invariants

- Firestore collections/documents, current → legacy request order, acknowledgement writes, request IDs, and protocol-v2 metadata are unchanged.
- Duplicate current/legacy requests and applied markers still short-circuit at the same point. Null pending records still reject before writes, allowing the existing listener/reconciliation retry policy to own recovery.
- Legacy request records may still omit the discriminator; the decoder supplies the canonical discriminator. Missing preference arrays normalize to the transform's existing empty-list fallback.
- Waitlist values other than `cancel`/`join` or the three known attendance values normalize to the same join/interested behavior previously selected by the consumer.
- Malformed cloud envelopes or collection containers return the existing no-cloud-record result instead of becoming a falsely typed management state.
- Request identity is never inferred, Firestore paths are never broadened, and no authorization, schema, publication, or player-management transform changed.
