# REF-009 - Establish and migrate to a shared sync core

Status: active

## Objective

Give API and Electron player snapshot/request transformations one runtime owner while preserving API validation, Electron fallback behavior, renderer-owned management semantics, Player protocol-v2 compatibility, public payloads, account isolation, ordering, and failure behavior.

## Boundary decision

- `apps/api/src/orbitCore.js` is the existing pure, deployment-contained server core. The API is a separate CommonJS package and has separately rooted Vercel metadata; moving its runtime dependency above `apps/api/` would require an unverified deployment packaging decision.
- Electron duplicates the server algorithm in `electron/main.cjs`. It can consume the API-owned pure module when that exact file is added to the Electron package allowlist.
- `src/lib/playerSync.ts` is not behaviorally interchangeable with the server algorithm. Repository evidence shows different club-ID precedence, membership notes/projection, full-table attendance, invalid table-ID handling, and canonical input assumptions. It remains the typed renderer owner rather than silently changing product/data behavior.
- Player owns request construction, hydration, and commit/revision selection. REF-009 does not move Expo source outside `player-app/`, widen Metro watch roots, or change Firestore/API schemas.

## Sequence

| Subtask | Scope | Required characterization |
| --- | --- | --- |
| REF-009A | Cross-runtime behavior inventory | API/Electron parity, explicit compatibility differences, renderer divergence, account isolation, ordering, immutability |
| REF-009B | Shared API/Electron core migration | unchanged API exports, explicit Electron profile, packaged-file inclusion, direct core tests, Electron check-JS |
| REF-009C | Protocol and ownership audit | protocol-v2 child-first/commit-marker tests, Player legacy fallback, complete diff and documentation review |

## Safety

- Characterization must be committed against unchanged production owners before moving Electron behavior.
- Do not start Electron or the API, bind a socket, read the tracked database, contact Firebase/API/Stripe, run the stress harness, package/publish a release, or deploy.
- Preserve API `validateStatePayload` behavior and Electron's existing no-validation transform boundary.
- Preserve API request-ID fallbacks and Electron random-ID fallbacks even though normal routes require authoritative IDs.
- Preserve all renderer behavior; only a future product/data decision may reconcile the documented semantic differences.

### REF-009B - Shared API/Electron core migration

- Moved the pure implementation to `apps/api/src/shared/orbitCore.cjs`; `apps/api/src/orbitCore.js` remains the unchanged public API entrypoint.
- Added an explicit Electron profile that disables API-boundary state validation and preserves Electron's random fallback IDs and legacy membership projection. Default exports retain API validation, request-ID fallback, and current projection behavior.
- `electron/main.cjs` now wires the shared profile and no longer owns the duplicated snapshot/membership/waitlist algorithms. The main process is 505 lines, down from 853.
- Electron packaging includes only the pure `.cjs` core file; the focused static test pins the import, profile settings, removed local owners, and allowlist entry.
- Verification after implementation: four focused files / 45 tests, all four root compiler projects, Player TypeScript, all 48 files / 280 tests, the 1,930-module renderer build, and `npm run verify` passed.
- No Electron process, API server, socket, package/release build, tracked database, Firebase/API/Stripe endpoint, credential, or hosted service was invoked.

## Acceptance

- API callers retain their existing exports and behavior; Electron uses an explicit compatibility profile from the same source.
- Electron packaging includes only the required pure shared-core file, with a static assertion guarding the allowlist.
- Renderer, API, Electron, and Player protocol characterization remains green; all compiler projects, tests, build, and `npm run verify` pass.
- Documentation identifies every sync responsibility that remains intentionally runtime-specific.
