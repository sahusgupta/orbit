## Initial polling attempt, superseded before publication

Only the hosted desktop-state poll cadence changes: a visible desktop performs its initial read, then schedules a new read 30 seconds after completion. Hidden documents pause scheduled reads. Failed, unavailable, or non-authoritative responses retry with bounded exponential delay, and visibility changes retain the retry deadline. Save-pending, stale-response, tenant, authoritative-state, cancellation, and no-overlap safeguards remain in place. The separate browser/local bridge poll is unchanged.

This reduces scheduled refresh frequency by about 90% under steady foreground use; actual Firestore read reduction depends on other operations and the number of documents loaded. Incoming player operations can take up to approximately 30 seconds plus request latency to appear. Existing installations require the desktop update before they gain this behavior.

Commit `758227d07e3ccebd4434ae55fac446e944003da0` preserved that initial implementation in [PR 37](https://github.com/sahusgupta/orbit/pull/37), stacked on the prior SDK 58 preparation branch. It was not published. The subsequent user instruction supersedes this polling-only design.

## Immediate incoming changes with fewer idle reads

The API adds authenticated `GET /state/:venueId/events`. It watches exactly one server-only authoritative account header with Firebase Admin, so commits from other API instances are observed. It sends only revision notifications, never player state, credentials, or raw errors. Existing client authentication and tenant checks apply initially and before each change notification. Streams have 15-second heartbeats, a 45-second maximum lifetime, credential-expiry bounds, bounded per-process capacity, and cleanup on disconnect, failure, expiry, or backpressure. `ORBIT_MANAGEMENT_SSE_MAX_CONNECTIONS` optionally sets the per-process capacity (default 50, bounded 1–500). Memory mode never initializes Admin; tests inject a watcher.

Electron owns the authenticated streaming connection, parser limits, reconnect backoff, and lifecycle cleanup. The preload exposes only typed revision/status notifications, with fixed IPC channels and opaque per-document subscription IDs. Account changes, credential rotation or trusted expiry renewal, document navigation, renderer destruction, and application shutdown release the prior subscription. A `ready` control frame alone does not declare the stream healthy: the first valid header revision is required, and ready/heartbeat frames cannot extend the initial ten-second deadline or continually reset failure backoff. Keys remain in request headers, and the stream never writes state or the local cache.

The renderer triggers its existing authenticated authoritative loader immediately when a newer revision arrives. It deduplicates and coalesces notifications, retains pending updates across in-flight reads and local saves, and keeps the existing state-reference/save/authority checks. Optimistic local actions retain priority while saving; the renderer does not invent another player's unknown state from a revision number. Incoming fields render as soon as the authoritative response arrives, without a 30-second timer. Healthy connections use a five-minute full-read watchdog measured from the last accepted read; reconnects cannot postpone that deadline. Disconnected or older clients retain a three-second polling fallback. Failed reads back off through 60/120/240/300 seconds. Hidden windows close their stream and pause reads; the separate browser/local bridge remains at 1.5 seconds.

The API must be staged, tested, and promoted before the desktop release. No Firebase rules, collections, persisted shapes, publication commit markers, or state authority are changed.
