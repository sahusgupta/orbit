## Confirmed trigger and small scope

`PlayerApp.tsx` passes Match retry through the existing refresh action. `OrbitMatchScreen.tsx` keeps Refresh Match games available while secure storage is still restoring. The controller's `retry()` calls `start()` when `ready` is false, but each `start()` independently reads and subsequently assigns its saved journal. A late second non-null journal can therefore replace newer accepted pending operations after the first restoration read has completed. Storage reads are asynchronous and are not part of the required-write queue.

The intended fix coalesces initialization so overlapping Start/Retry cannot restore an old journal over newer work. Early saves must remain rejected until restoration succeeds; a failed journal read must remain retryable; disposal, owner isolation, durable mutation identities, remote retry, preference conflict reconciliation and terminal-listener recovery must retain their existing behavior. No API, schema, rules, authorization, native configuration, dependency or visual change is in scope.
